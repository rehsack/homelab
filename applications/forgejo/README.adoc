= Forgejo Deployment

Git-Forge auf Basis von Forgejo (SQLite, rootless) im Namespace `soho`.

== Deployment

[source,bash]
----
kubectl apply -f applications/forgejo/namespace.yaml
kubectl apply -f applications/forgejo/forgejo-pvc.yaml
kubectl apply -f applications/forgejo/forgejo-config.yaml
kubectl apply -f applications/forgejo/forgejo-secret.yaml
kubectl apply -f applications/forgejo/forgejo-deployment.yaml
kubectl apply -f applications/forgejo/forgejo-service.yaml
----

== Admin-User erstellen

Credentials aus dem KeePass-Tresor holen und den Admin-User anlegen:

[source,bash]
----
ADMIN_USER=$(bin/kdbx-fetch cred --entry forgejo/admin --attribute UserName --quiet)
ADMIN_PASS=$(bin/kdbx-fetch cred --entry forgejo/admin --attribute Password --quiet)
ADMIN_MAIL=$(bin/kdbx-fetch cred --entry forgejo/admin --attribute URL --quiet)

kubectl -n soho exec deploy/forgejo -- \
  forgejo admin user create \
    --admin \
    --username "${ADMIN_USER}" \
    --password "${ADMIN_PASS}" \
    --email "${ADMIN_MAIL}" \
    --must-change-password=false
----

Der Befehl ist idempotent — bei erneutem Aufruf meldet er, dass der User bereits existiert.

== ConfigMap aktualisieren

Die ConfigMap ist nur die Vorlage für den ersten Start: Der Init-Container kopiert sie,
wenn im PVC noch keine `app.ini` liegt. Danach ergänzt Forgejo dort selbst erzeugte
Secrets (`INTERNAL_TOKEN`, `[oauth2] JWT_SECRET`) — die Datei im PVC ist ab dann der
Stand, die ConfigMap nicht.

WARNING: Die `app.ini` im PVC *nicht* löschen. Forgejo erzeugt die Secrets sonst neu;
ein neues `JWT_SECRET` macht alle OAuth2-Tokens ungültig.

Eine Änderung deshalb an beiden Stellen nachziehen — in der ConfigMap (für eine
Neuinstallation) und gezielt in der Datei im PVC:

[source,bash]
----
kubectl apply -f applications/forgejo/forgejo-config.yaml
kubectl -n soho exec deploy/forgejo -c forgejo -- \
  sed -i '/^\[repository\]/a KEY = value' /var/lib/gitea/custom/conf/app.ini
kubectl -n soho rollout restart deploy/forgejo
----

== Storage

Das PVC `forgejo-data` ist unabhängig vom Pod und Deployment.
Daten bleiben erhalten, solange das PVC existiert — auch wenn das Deployment gelöscht und neu erstellt wird.

CAUTION: Die StorageClass `rook-ceph-block` hat `reclaimPolicy: Delete`.
Wird das PVC gelöscht, werden auch die Daten unwiderruflich entfernt.

Das PVC liegt auf `rook-ceph-block` (RBD, ext4): SQLite gehört auf Block, nicht auf
CephFS (arc42 ADR-H-009). Umgezogen am 2026-10-26 — Verfahren unten.

=== PVC einsehen

[source,bash]
----
kubectl -n soho get pvc
kubectl -n soho describe pvc forgejo-data
----

=== PVC vergrößern (online, ohne Datenverlust)

Die StorageClass hat `allowVolumeExpansion: true`.
Größe in `forgejo-pvc.yaml` anpassen (z.B. `50Gi` → `100Gi`) und applyen:

[source,bash]
----
kubectl apply -f applications/forgejo/forgejo-pvc.yaml
----

Ceph-CSI vergrößert das RBD-Image und danach das ext4 im laufenden Pod — kein Neustart nötig.

=== Belegung überblicken

Gesamtkapazität und Belegung je Pool:

[source,bash]
----
kubectl -n rook-ceph exec deploy/rook-ceph-tools -- ceph df
----

RBD-Images (entsprechen den PVCs) mit tatsächlich belegtem Platz:

[source,bash]
----
kubectl -n rook-ceph exec deploy/rook-ceph-tools -- rbd du -p replicapool
----

=== PVC auf eine andere StorageClass umziehen

PVC-Namen und StorageClass sind unveränderlich; so bleibt der Name `forgejo-data` und das
Deployment unberührt, und die alten Daten bleiben bis zum Schluss erhalten:

. Forgejo auf 0 skalieren (SQLite konsistent).
. Altes PV auf `persistentVolumeReclaimPolicy: Retain` patchen, PVC `forgejo-data` löschen,
  `claimRef` vom PV entfernen.
. Das alte PV als statisches PVC `forgejo-data-old` (`volumeName`) neu binden.
. `forgejo-pvc.yaml` mit der neuen StorageClass applyen.
. Hilfs-Pod (uid/gid 1000) mit beiden PVCs: `cp -a /old/. /new/`, dann Dateiliste und
  `md5sum` beider Seiten vergleichen.
. Forgejo starten und prüfen; erst danach `forgejo-data-old` und das alte PV löschen
  (PV vorher auf `Delete` zurückstellen, damit Ceph-CSI das Volume mit entfernt).

=== Pod-zu-PVC-Zuordnung

Alle PVCs clusterübergreifend:

[source,bash]
----
kubectl get pvc -A
----

Welcher Pod nutzt welches PVC:

[source,bash]
----
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{"\t"}{range .spec.volumes[*]}{.persistentVolumeClaim.claimName}{" "}{end}{"\n"}{end}'
----
