= Forgejo Deployment

Git-Forge auf Basis von Forgejo (SQLite, rootless) im Namespace `soho`.

== Deployment

[source,bash]
----
kubectl apply -f applications/forgejo/namespace.yaml
kubectl apply -f applications/forgejo/forgejo-pvc.yaml
kubectl apply -f applications/forgejo/forgejo-config.yaml
kubectl apply -f applications/forgejo/forgejo-secret.yaml
kubectl apply -f applications/forgejo/forgejo-deployment.yaml
kubectl apply -f applications/forgejo/forgejo-service.yaml
----

== Admin-User erstellen

Die Credentials liegen SOPS-verschlüsselt in `forgejo-secret.yaml` (Schlüssel
`FORGEJO_ADMIN_USER`, `FORGEJO_ADMIN_PASSWORD`, `FORGEJO_ADMIN_EMAIL`):

[source,bash]
----
f=applications/forgejo/forgejo-secret.yaml
get() { sops -d --extract "[\"stringData\"][\"$1\"]" "$f"; }

kubectl -n soho exec deploy/forgejo -c forgejo -- \
  forgejo admin user create \
    --admin \
    --username "$(get FORGEJO_ADMIN_USER)" \
    --password "$(get FORGEJO_ADMIN_PASSWORD)" \
    --email "$(get FORGEJO_ADMIN_EMAIL)" \
    --must-change-password=false
----

Der Befehl ist idempotent — bei erneutem Aufruf meldet er, dass der User bereits existiert.

Nur das Passwort, etwa zum Anmelden, direkt in die Zwischenablage:
`sops -d --extract '["stringData"]["FORGEJO_ADMIN_PASSWORD"]' applications/forgejo/forgejo-secret.yaml | pbcopy`

== Verwaltung: `exec` oder API-Token

`forgejo admin …` per `kubectl exec` läuft im Pod direkt gegen die Datenbank und braucht
*keine* Forgejo-Credentials — berechtigt ist, wer per `kubectl` in `soho` darf:

[source,bash]
----
kubectl -n soho exec -it deploy/forgejo -c forgejo -- \
  forgejo admin user create --username <user> --email <mail> \
    --random-password --must-change-password
----

Das Einmal-Passwort gehört dem neuen User, nicht ins Repository.

Für Skripte gegen die REST-API ein Token statt des Admin-Passworts — einzeln
widerrufbar, Scopes nur so weit wie nötig. Es wird erst angelegt, wenn ein Skript es
braucht (ein ungenutztes Token ist nur Angriffsfläche), und geht dann direkt
verschlüsselt in `forgejo-secret.yaml`:

[source,bash]
----
kubectl -n soho exec deploy/forgejo -c forgejo -- \
  forgejo admin user generate-access-token --username <admin> \
    --token-name <zweck> --scopes write:admin --raw \
  | jq -R . \
  | sops set --value-stdin applications/forgejo/forgejo-secret.yaml '["stringData"]["FORGEJO_API_TOKEN"]'
----

Widerrufen: im Web-UI unter _Einstellungen → Anwendungen_ des Token-Inhabers, danach
den Schlüssel mit `sops unset` aus der Datei entfernen.

== ConfigMap aktualisieren

Die ConfigMap ist nur die Vorlage für den ersten Start: Der Init-Container kopiert sie,
wenn im PVC noch keine `app.ini` liegt. Danach ergänzt Forgejo dort selbst erzeugte
Secrets (`INTERNAL_TOKEN`, `[oauth2] JWT_SECRET`) — die Datei im PVC ist ab dann der
Stand, die ConfigMap nicht.

WARNING: Die `app.ini` im PVC *nicht* löschen. Forgejo erzeugt die Secrets sonst neu;
ein neues `JWT_SECRET` macht alle OAuth2-Tokens ungültig.

Eine Änderung deshalb an beiden Stellen nachziehen — in der ConfigMap (für eine
Neuinstallation) und gezielt in der Datei im PVC:

[source,bash]
----
kubectl apply -f applications/forgejo/forgejo-config.yaml
kubectl -n soho exec deploy/forgejo -c forgejo -- \
  sed -i '/^\[repository\]/a KEY = value' /var/lib/gitea/custom/conf/app.ini
kubectl -n soho rollout restart deploy/forgejo
----

== Upgrade (Snapshot → Upgrade → Test → ggf. Rollback)

Das Image ist auf den exakten Patch gepinnt (`forgejo-deployment.yaml`). Forgejo
unterstützt den direkten Sprung auf die Zielversion, die Migrationen laufen beim Start;
vorher die Breaking Changes aller übersprungenen Majors lesen
(`release-notes-published/<version>.md` im Forgejo-Repo, Upgrade-Guide in der Doku).

Das RBD-Image hinter dem PVC, für die `rbd`-Befehle unten (alle per
`kubectl -n rook-ceph exec deploy/rook-ceph-tools --`):

[source,bash]
----
PV=$(kubectl -n soho get pvc forgejo-data -o jsonpath='{.spec.volumeName}')
IMG=$(kubectl get pv $PV -o jsonpath='{.spec.csi.volumeAttributes.pool}/{.spec.csi.volumeAttributes.imageName}')
----

. Image auf beiden Knoten vorab ziehen (Image-Volume-DaemonSet, wie bei Rook —
  `infrastructure/rook-ceph/README.md`), dann `forgejo manager flush-queues`.
. Baseline: `forgejo doctor check --all` — Befunde von vorher sind dann keine
  Upgrade-Folgen.
. Forgejo auf 0, warten bis `rbd status $IMG` *keine* Watchers mehr zeigt (Volume
  ausgehängt, SQLite konsistent), dann `rbd snap create $IMG@pre-forgejo-<version>`.
. Image-Tag in `forgejo-deployment.yaml` setzen, `kubectl apply`.
. Prüfen: Migrations-Log ohne Fehler, `forgejo doctor check --all`, Login und ein
  typischer Ablauf im Web-UI.
. *Rollback*, falls etwas nicht stimmt: Forgejo auf 0, warten bis keine Watchers,
  `rbd snap rollback $IMG@pre-forgejo-<version>`, alten Tag zurück, `kubectl apply`.
  Ein Downgrade *ohne* Rollback verweigert Forgejo (Datenbank-Version).
. Wenn alles passt: `rbd snap rm $IMG@pre-forgejo-<version>` — ein Snapshot ist kein
  Backup und wird mit der Zeit teuer.

`doctor` scheitert an `data/gitea/repositories` und `log/`, solange es kein Repository
bzw. kein Datei-Log gibt; leer anlegen, dann laufen alle Checks. „Garbage collect LFS"
meldet `ERROR`, solange LFS aus ist.

== Storage

Das PVC `forgejo-data` ist unabhängig vom Pod und Deployment.
Daten bleiben erhalten, solange das PVC existiert — auch wenn das Deployment gelöscht und neu erstellt wird.

CAUTION: Die StorageClass `rook-ceph-block` hat `reclaimPolicy: Delete`.
Wird das PVC gelöscht, werden auch die Daten unwiderruflich entfernt.

Das PVC liegt auf `rook-ceph-block` (RBD, ext4): SQLite gehört auf Block, nicht auf
CephFS (arc42 ADR-H-009). Umgezogen am 2026-10-26 — Verfahren unten.

=== PVC einsehen

[source,bash]
----
kubectl -n soho get pvc
kubectl -n soho describe pvc forgejo-data
----

=== PVC vergrößern (online, ohne Datenverlust)

Die StorageClass hat `allowVolumeExpansion: true`.
Größe in `forgejo-pvc.yaml` anpassen (z.B. `50Gi` → `100Gi`) und applyen:

[source,bash]
----
kubectl apply -f applications/forgejo/forgejo-pvc.yaml
----

Ceph-CSI vergrößert das RBD-Image und danach das ext4 im laufenden Pod — kein Neustart nötig.

=== Belegung überblicken

Gesamtkapazität und Belegung je Pool:

[source,bash]
----
kubectl -n rook-ceph exec deploy/rook-ceph-tools -- ceph df
----

RBD-Images (entsprechen den PVCs) mit tatsächlich belegtem Platz:

[source,bash]
----
kubectl -n rook-ceph exec deploy/rook-ceph-tools -- rbd du -p replicapool
----

=== PVC auf eine andere StorageClass umziehen

PVC-Namen und StorageClass sind unveränderlich; so bleibt der Name `forgejo-data` und das
Deployment unberührt, und die alten Daten bleiben bis zum Schluss erhalten:

. Forgejo auf 0 skalieren (SQLite konsistent).
. Altes PV auf `persistentVolumeReclaimPolicy: Retain` patchen, PVC `forgejo-data` löschen,
  `claimRef` vom PV entfernen.
. Das alte PV als statisches PVC `forgejo-data-old` (`volumeName`) neu binden.
. `forgejo-pvc.yaml` mit der neuen StorageClass applyen.
. Hilfs-Pod (uid/gid 1000) mit beiden PVCs: `cp -a /old/. /new/`, dann Dateiliste und
  `md5sum` beider Seiten vergleichen.
. Forgejo starten und prüfen; erst danach `forgejo-data-old` und das alte PV löschen
  (PV vorher auf `Delete` zurückstellen, damit Ceph-CSI das Volume mit entfernt).

=== Pod-zu-PVC-Zuordnung

Alle PVCs clusterübergreifend:

[source,bash]
----
kubectl get pvc -A
----

Welcher Pod nutzt welches PVC:

[source,bash]
----
kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{"\t"}{range .spec.volumes[*]}{.persistentVolumeClaim.claimName}{" "}{end}{"\n"}{end}'
----
